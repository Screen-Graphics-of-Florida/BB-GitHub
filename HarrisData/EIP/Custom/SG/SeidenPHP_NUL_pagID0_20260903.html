What this is

79 XML rows in HDSSTDPGM end with a stray NUL byte after the closing root tag: 27 docsets in SYDCST and 52 page designs in SYDSGN. SeidenPHP hands that byte to PHP, libxml rejects it as content after the root element, simplexml_load_string() returns null, and the page fatals to a blank screen. ZendServer's CCSID conversion drops the byte, which is why the same pages work today. The XML is invalid either way. This report covers the 25 of those 52 that sit at page ID 0.

Page ID 0 means the default page - the one hdList.php serves when no page ID is passed. PageMaintain.php line 687 allocates HD-flagged pages below 99 and customer-created pages from 100 up, so page ID 0 is Harris supplied by construction, not by inference. All 25 carry DSRSVD blank and DSCRTB = Sys_Gen.

A docset marked DEFECTIVE means the table is broken on both ends - the docset fails to load before the page XML is ever read, so those 11 tables return 500 no matter which page is requested. The other 14 fail only on the default view.

Three things worth attention

  • 145 and 199 are the menu maintenance screens themselves. SYURLM (URL Master) and SYPORT04 (Portal). Under SeidenPHP both return 500, so the ability to repair menus from inside the portal is lost at exactly the moment it would be needed. They are also the only two rows carrying a user restriction (PDUSER = BILL); the other 23 are unrestricted.
  • The write side is the likely source, and it is not one screen. Eighteen of the 25 were last written by a named profile - BILL (7), RDBHRPR (5), CDUROCHER and MMORGAN (2 each), LBELL, SMCCONNELL - and seven by Sys_Gen. So both the interactive PageMaintain.php save and the Sys_Gen publish path produce the NUL, which points at a shared XML generation routine rather than one page. This is a hypothesis consistent with the data, not a proven mechanism. Confirming it needs the generator read directly, or a save-and-rehex test against a scratch page.
  • The spread is broad, not clustered. AR, payroll, inventory, MRP, costing and warehouse are all represented, which matches the overall rate of roughly one list page in fifteen. That is the failure mode most likely to be misdiagnosed as "SeidenPHP is broken" rather than as bad data.
